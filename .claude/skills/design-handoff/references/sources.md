# Sources behind the design-handoff skill

Condensed from the Head-of-Product knowledge base (Lenny's Newsletter and Podcast archive, `02-prototyping-and-design/`) and Lune's Linear Usage Guide (`00-company-context/linear-usage-guide.md`).

## PM owns the why, designer owns the how
- "It's my belief that PMs are responsible for the 'why.'" When the why is clear, designers and engineers "can make really great decisions" locally; the Microsoft-era spec that tabulated every error state does not scale. Yuhki Yamashita, `how-figma-builds-product.md`, `yuhki-yamashata.md`. "You cannot specify everything that happens."
- PMs "clarify the context, defining problems, goals, and constraints, and tying it all back to the business"; "you should defer to them in their area of expertise: the user experience." Never say "my designer". Katie Dill, `the-pm--design-partnership.md`.
- One-pager contents: goals, delightful use cases, current failure modes, plus team principles naming key users and trade-offs. Cat Wu, `cat-wu.md`.
- Founding hypothesis: target customer in plain language, the important problem, competitors, two or three decision principles. `introducing-the-foundation-sprint-from-the-creators-of-the-design-sprint.md`.
- Strategy docs "wouldn't be complete without wireframes"; the nav-bar litmus test: what are the four or five things? Ravi Mehta, `ravi-mehta.md`.
- "Five things instead of the 15 things in a really, really great way"; be explicit about the learning phase. Jiaona Zhang, `jiaona-zhang.md`.

## Presenting a prototype as a starting point
- Set fidelity expectations explicitly before showing it. `how-to-get-your-entire-team-prototyping-with-ai.md`.
- Figma product reviews map the whole "option space" before debating one direction. `how-figma-builds-product.md`.
- Explain reasoning so others "extract principles" rather than receive verdicts. Jenny Wen, `jenny-wen.md`.
- An intentionally extreme prototype that was "never going to ship" started Slack's redesign. Tamar Yehoshua, `tamar-yehoshua.md`.

## Collaboration during design
- Include designers early, not assembly-line; protect maker time, meetings "blow a whole afternoon". `the-pm--design-partnership.md`.
- Daily hour-long PM–designer 1:1 during a 0-to-1 effort; build a single shared artifact rather than readout → crit → review as separate deliverables. Mihika Kapoor, `mihika-kapoor.md`.
- Designer time is now ~30–40% mocking and ~30–40% pairing with engineers. Jenny Wen, `jenny-wen.md`.
- Handoffs as pairing sessions, engineers in design syncs. `how-to-ship-like-a-startup.md` (folder 04).

## Crits vs reviews
- "Design crits are intended to be very generative, and are explicitly not about making decisions." ~10–15 min present, ~5 min questions, ~5 min silent written comments. Product reviews are decision meetings with two types (problem vs solution), PM-facilitated, using an alignment/voting widget so "the loudest people" don't decide. `how-figma-builds-product.md`.
- Multidisciplinary "walk the store" reviews scored on usability, utility, desirability; editing needs "courage"; "Almost, but no" is a valid outcome; "the gravitational pull is to mediocrity". Katie Dill, `katie-dill.md`.

## What "approved" should mean
- A decision-type review has occurred (`how-figma-builds-product.md`); deterministic states resolved, non-deterministic deferred to real-data testing (`jenny-wen.md`); designs point to the design system in code because AI-written code "is not always picking up stuff in the design system" (`jenny-wen.md`); the prototype travels as a communication aid, not code (`how-to-get-your-entire-team-prototyping-with-ai.md`); an editor has said good enough (`katie-dill.md`).
- Linear Usage Guide: UX/UI Design "closes when designs are approved and handed to engineering"; FE and BE design start together once UX is approved and carry aligned target dates; every issue has a milestone, Team and label.

## Anti-patterns
- Spec-as-contract (`yuhki-yamashata.md`); overriding designers on taste, "my designer", design goals vs business goals, waterfall handoff (`the-pm--design-partnership.md`, `katie-dill.md`); chasing every prototype into "a Frankenstein product" (`aparna-chennapragada.md`).
